# 地图旋转需求实现与排障说明

本文档依据截至 2026-08-12 工作区中的本地未提交代码整理，记录地图对齐旋转从协议字段、Step2 调整与擦除区下发，到 Step3 区域编辑、Step4/任务预览显示、开始打磨规划避障区交互及坐标下发的完整实现。其目的不是描述理想方案，而是给后续问题排查提供与当前代码一致的入口。

> 范围说明：本地工作区同时包含地图擦除、障碍物下发、页面生命周期、日志和生成协议代码等修改。本文只记录与地图旋转直接相关，或因旋转而必须联动调整的代码。文中“已实现”均指当前本地修改，尚不代表已经提交、联调或验收通过。

---

## 1. 需求与最终效果

地图旋转需求包含以下闭环：

1. Step2 能读取后端返回的已有对齐角，允许用户通过纵向滑轨及 `+/-` 按钮调整地图角度，范围限制为 `[-180°, 180°]`。
2. 地图、机器人标记和擦除选区在旋转后仍保持正确的视觉位置、朝向和交互方向。
3. 点击 Step2“下一步”时，将当前角度通过地图对齐请求下发给下位机。
4. 后续地图预览、区域设置、路径规划及任务执行页面读取后端返回的两个旋转字段，按同一规则显示。
5. Step2 擦除区、Step3 工作区/禁区和开始打磨规划避障区统一采用稳定手势模型，在地图旋转、缩放和平移后仍保持跟手、按钮可见和边界受控。
6. 屏幕交互几何与最终下发几何分离：修复拖动、缩放和按钮位置时，不改变已经验证正确的 Bitmap/TCP/世界坐标转换链和点序。

当前统一使用的地图总旋转角为：

```text
totalRotation = alignmentYawDeg + rotationAlignmentDeltaDeg
```

- `alignmentYawDeg`：地图已有的对齐偏航角。
- `rotationAlignmentDeltaDeg`：后端返回的旋转对齐增量。
- Step2 编辑期间使用 UI 状态 `alignmentYaw`，初始值同样取上述两者之和；用户调整后，下发的是当前 `alignmentYaw`。

如果页面只使用其中一个字段，或者重复叠加某个字段，会出现不同步骤之间角度不一致的问题。

## 2. 数据链路

### 2.1 后端响应到状态模型

地图快照、地图预览和路径规划响应都增加并透传了：

```kotlin
alignmentYawDeg: Float
rotationAlignmentDeltaDeg: Float
```

主要链路如下：

```text
SlLink 协议响应
  └─ SlLinkManager 解析
      ├─ MapImagePayload / MapImageStream
      ├─ MapPreviewPayload / MapPreviewStream
      └─ PathPlanPayload / PathPlanStream
          └─ 各页面 ViewModel 写入 MapGeo 或页面模型
              └─ UI 计算 totalRotation 并渲染
```

关键文件：

- `core/model/.../MapImageStream.kt`
- `core/model/.../MapPreviewStream.kt`
- `core/model/.../PathPlanStream.kt`
- `core/tcp/.../SlLinkManager.kt`
- `feature/map/.../MapScreenStep2ViewModel.kt`
- `feature/map/.../MapScreenStep3ViewModel.kt`
- `feature/map/.../MapScreenStep4ViewModel.kt`
- `feature/map/.../MapHomeViewModel.kt`

`MapImagePayload` 和 `MapPreviewPayload` 自定义了 `equals/hashCode`，新增字段也已加入比较和哈希计算。排查“响应角度已变化但 StateFlow/UI 不刷新”时，需要首先确认这两处没有漏掉字段。

### 2.2 Step2 角度调整与下发

Step2 请求地图预览后：

```kotlin
alignmentYaw = payload.alignmentYawDeg + payload.rotationAlignmentDeltaDeg
```

UI 中 `MapRotationController` 提供两种调整方式：

- `+/-` 按钮每次调整 `1°`。
- 纵向拖动按滑轨高度映射到 `360°`；向上拖动增加角度，向下拖动减小角度。

`updateAlignmentYaw` 和 `adjustAlignmentYaw` 都将结果限制在 `[-180°, 180°]`。

点击“下一步”时，`MapScreenStep2ViewModel.sendEditedDataToEmbeddedOnNextStep()` 调用：

```text
TcpManager.sendMapAlignment(mapId, alignmentYaw)
  └─ SlLink.MapAlignmentRequest(map_id, rotation_deg)
      └─ SlLinkManager.requestMapAlignment(...)
          └─ SlMessageBuilder.buildMapAlignmentRequestRaw(...)
              └─ SL-Link 消息 ID 0x0524
```

相关日志统一使用 `MapAlignment_Debug`。下发异常时建议按以下顺序搜索：

1. `sendEditedDataToEmbeddedOnNextStep 被调用了`
2. `正在下发对准角`
3. `TcpManager.sendMapAlignment 开始组包`
4. `物理发包结果`

若第 1 条不存在，应检查 Step2 下一步按钮回调和导航调用；若前 3 条存在但物理发包失败，应检查 TCP 连接及帧发送；若发包成功但后续页面角度未变化，应检查下位机是否保存并在预览/规划响应中返回两个角度字段。

## 3. 坐标系和变换约定

### 3.1 坐标空间

当前地图交互涉及四类坐标：

1. **Content/Bitmap 坐标**：解码后地图图片的像素坐标，原点在左上角。区域编辑的几何数据主要保存在此空间。
2. **Canvas/Screen 坐标**：经过适配缩放、平移、用户缩放和平移、地图旋转后的显示及指针坐标。
3. **TCP 地图像素坐标**：协议中地图原始宽高对应的像素坐标；当解码尺寸和原始地图尺寸不同，需要按比例换算。
4. **世界坐标**：以米为单位，由地图分辨率、原点和坐标轴方向换算，最终用于区域下发。

### 3.2 Step3 正反向点变换

设：

- `Rθ(p)` 表示点 `p` 绕地图中心旋转 `θ`。
- `baseScale/baseOffset` 表示地图适配容器的缩放和平移。
- `mapZoom/mapPan` 表示用户手势产生的缩放和平移。
- `θ = totalRotation`。

Content 到 Screen：

```text
rotated = Rθ(content)
fitted  = rotated * baseScale + baseOffset
screen  = fitted * mapZoom + mapPan
```

Screen 到 Content 必须严格逆序：

```text
fitted  = (screen - mapPan) / mapZoom
rotated = (fitted - baseOffset) / baseScale
content = R-θ(rotated)
```

对应实现是 `MapScreenStep3.kt` 中的 `toScreenPoint` 和 `toContentPoint`。Canvas 的 `withTransform` 顺序也与此保持一致：

```kotlin
translate(mapPan)
scale(mapZoom)
translate(baseOffset)
scale(baseScale)
rotate(totalRotation, pivot = bitmapCenter)
```

### 3.3 屏幕拖动增量不能统一套用一个公式

拖动回调给出的位移属于屏幕空间，但是否需要按 `-totalRotation` 反向旋转，取决于被编辑几何保存在哪个空间，而不是取决于底图是否旋转：

| 场景 | 编辑几何空间 | 屏幕累计位移换算 |
| --- | --- | --- |
| Step2 擦除区 | 已对齐、屏幕轴方向的 UI Content | 只除以 `zoom * baseScale`，不反向旋转 |
| Step3 工作区/禁区 | 未旋转 Bitmap Content | 先按 `-totalRotation` 旋转，再除以 `mapZoom * baseScale` |
| StartGrinding 规划避障区 | 面板基础 Model，图形保持屏幕轴对齐 | 只除以手势开始时的 Viewport scale，不反向旋转 |

Step3 的典型换算为：

```text
contentDelta = R-totalRotation(screenDelta)
               / (mapZoom * baseScale)
```

Step2 和 StartGrinding 的典型换算为：

```text
alignedOrModelDelta = screenDelta / totalScale
```

如果屏幕轴对齐图形错误叠加 `-totalRotation`，地图旋转 90° 后就会出现“向右拖却向上/下移动”；如果 Step3 的真实 Content 图形遗漏反向旋转，则会出现相反问题。排障时必须先确认几何空间，再决定是否撤销地图旋转。

### 3.4 统一的稳定手势模型

Step2、Step3 和 StartGrinding 的活动图形都遵循以下交互模型：

1. 手势开始时记录图形起始几何、命中层位置、总缩放以及旋转参考点等快照。
2. 手势过程中累计原始屏幕位移，候选几何始终使用“起始几何 + 累计位移”计算，不能在每一帧基于已经变化的控件位置继续叠加局部 delta。
3. 固定手势命中层，不让命中 Box 随动态预览重组移动；图形和按钮只作为可见预览跟随候选几何。
4. 在屏幕空间按真实可见几何做边界钳制，越界时停在最近合法位置；指针反向移动后应立即恢复跟随。
5. 手势结束后清除起始快照；取消时恢复起始几何或结束当前预览。

该模型解决两个同源问题：动态图形移动抵消逐帧拖动量导致“不跟手”，以及右下角缩放按钮随重组移出原命中层后消失或丢失事件。

## 4. Step2 实现

### 4.1 地图和机器人显示

`MapScreenStep2.kt` 在地图图片的 `withTransform` 中绕图片中心执行：

```kotlin
rotate(degrees = alignmentYaw, pivot = contentCenter)
```

点坐标转换使用同一旋转中心：

- `toContentPoint` 使用 `-alignmentYaw`。
- `toScreenPoint` 使用 `+alignmentYaw`。

机器人中心位置通过 `toScreenPoint(bitmapPoint)` 计算；机器人图标朝向使用：

```text
displayHeading = robotHeading - alignmentYaw
```

这里减去地图旋转是为了避免地图旋转后机器人相对地图的朝向被重复旋转。

### 4.2 擦除选区

Step2 的活动擦除区使用独立的“已对齐 UI 矩形”。它的上下左右始终与屏幕一致，不通过修改未旋转 Bitmap 矩形再生成旋转包围框。地图旋转只影响底图轮廓和最终点位回算，不影响用户看到的移动方向、缩放方向或四角按钮方向。

当前交互策略是：

1. 将原地图四角绕 Bitmap 中心按 `alignmentYaw` 旋转，对四角取 `min/max`，得到已对齐 Content 中的地图轴对齐外接矩形 `rotatedMapBounds(...)`。
2. 活动擦除框的创建、移动和右下角缩放均限制在该外接矩形内；该范围允许进入旋转地图真实轮廓外侧的三角空白区域，这是当前产品约定。
3. 手势开始时固定移动区或缩放按钮的命中层，并保存 `gestureStartRect`；拖动过程中以累计屏幕位移计算动态预览。
4. 屏幕累计位移只除以 `zoom * baseScale`，不按地图角度反向旋转。移动使用整个矩形限位；缩放固定左上角并限制最小尺寸和右/下边界。
5. 删除、确认、缩放按钮始终锚定动态 UI 矩形的对应角点，命中层与可见按钮分离，避免按钮在拖动中消失或抵消位移。
6. 确认时按左上、右上、右下、左下顺序，将 UI 矩形四角保存到 `EraseRectArea.alignedCorners`。

下发转换保持以下既有闭环，不应因为修改 UI 交互而改动：

```text
UI 左上、右上、右下、左下
→ alignedCorners
→ 绕 Bitmap 中心按 -alignmentYaw 反向旋转
→ Bitmap 像素按宽高比例映射到 TCP 地图像素
→ 翻转 Y 轴并应用 resolution/origin/heading
→ 按原点序生成世界坐标并发送
```

这一设计用于同时保证：

- 用户看到的擦除区域与实际透明擦除显示一致。
- 下发给嵌入式的点仍处于原地图/世界坐标系。
- 已确认区域在角度存在时不会因只保存轴对齐 `left/top/right/bottom` 而丢失实际四角。

排查擦除区域偏移时，应逐层打印或断点核对：

```text
屏幕四角
→ alignedCorners
→ 反向旋转后的 bitmapCorners
→ TCP 地图像素
→ 世界坐标（米）
```

不要直接把屏幕轴对齐框当作未旋转 Bitmap 矩形，也不要为了修复跟手问题修改 `bitmapAreaToWorldOutput()` 中的旋转方向、Bitmap 中心、尺寸比例、Y 轴翻转或点位顺序。地图角度改变时，已确认区域的屏幕矩形保持不变，仅通过既有转换刷新下发输出。

## 5. Step3 实现

### 5.1 地图与所有已确认图形统一旋转

Step3 在同一个 Canvas 变换中绘制底图、已保存工作区、已确认工作区、矩形禁区和圆形禁区，并在变换末端绕图片中心应用 `totalRotation`。因此这些几何数据继续保存在未旋转 Content 坐标中，显示时由 Canvas 统一旋转。

机器人位置通过 `toScreenPoint` 映射，朝向使用：

```text
displayHeading = robotHeading - totalRotation
```

### 5.2 工作区和矩形禁区初始角度与位置

工作区矩形默认旋转角通过：

```text
boundaryRotationDeg = normalizeDegrees(-totalRotation)
```

初始化。这样地图已经旋转时，新建的工作区矩形在屏幕上仍保持水平。重置或切换相关状态时也应继续调用 `initialBoundaryRotationDeg()`，不能简单恢复为 `0f`。

新建矩形工作区的位置不再固定为 Content `(120, 120)`，而是由 `placeInitialBoundaryRect()` 计算：

1. 通过 `robotPoseToBitmapPoint(...)` 获得小车 Bitmap 中心，再经 `toScreenPoint(...)` 得到包含地图旋转、zoom 和 pan 的小车屏幕中心。
2. 优先保持约 `220 × 160 px` 的初始屏幕尺寸和 `60 × 60` Content 最小尺寸；地图外接矩形无法容纳时才缩小到可用范围。
3. 候选矩形以小车屏幕中心为中心；靠近边缘时整体移动到最近的完整可见位置。
4. 小车位置缺失、无效或落在地图范围外时，回退到旋转后地图屏幕外接矩形中心。
5. 将限位后的屏幕中心经 `toContentPoint(...)` 反算为 Content 中心，再写入 `boundaryTopLeft` 和 `boundarySize`。

该定位只在首次打开边界编辑器，以及从多边形切回矩形模式时执行。矩形出现后不会持续追随小车，多边形模式仍由用户点击添加顶点。

矩形禁区创建时现在使用相同补偿：

```kotlin
rotationDeg = initialBoundaryRotationDeg()
```

如果禁区仍使用 `ForbiddenShape.rotationDeg` 的默认值 `0f`，它会随 Canvas 再旋转一次 `totalRotation`，表现为工作区初始水平、禁区初始倾斜。排查两者初始方向不一致时，应优先检查创建 `ForbiddenShape` 的分支是否显式设置了补偿角，而不是修改统一 Canvas 旋转。

### 5.3 编辑态 Overlay 和手势命中区

区域几何数据位于 Content 空间，编辑控件位于 Compose Screen 空间。当前代码采取以下方式避免两者错位：

1. 使用 `rotatedRectCorners(...)` 在 Content 空间算出矩形自身旋转后的四角。
2. 使用 `toScreenPoint` 把每个角映射到屏幕。
3. 使用四角的 `min/max` 生成屏幕轴对齐 `gestureBounds`，作为手势开始时的命中区域。
4. `StableDragTarget`、`BoundaryZoomHandleButton` 和旋转手柄在手势开始后保持命中原点固定；图形及可见按钮通过动态预览或 `graphicsLayer` 位移继续跟随。
5. 关闭、确认、缩放按钮锚定当前屏幕几何对应角点，而不是锚定手势开始位置，因此拖动中不会消失。
6. 旋转按钮的可见位置位于屏幕包围框左下角，但旋转角计算使用真实矩形左下角作为参考，通过 `rotationReferenceHandleCenter` 修正两者差值。

这与旧文档中设想的“旋转整个 Box，并让 `rotationZ = rectRotation + totalRotation`”不同。当前实际代码没有依赖旋转后的 Compose Box 进行命中，而是使用屏幕轴对齐包围框，真实矩形四角仍单独参与旋转计算。排障时应以当前实现为准。

### 5.4 工作区矩形和矩形禁区

工作区矩形与矩形禁区采用相同的核心处理：

- 绘制：Content 四角随 Canvas 的 `totalRotation` 统一旋转。
- 移动：记录手势开始矩形，使用累计屏幕位移移动其屏幕包围框；先在父边界内钳制，再按 `-totalRotation` 和总缩放换算为 Content 位移。
- 缩放：累计屏幕位移投影到矩形当前可见宽、高轴；左上真实角保持锚定，候选真实四角的屏幕外接框必须位于父边界内。
- 旋转：固定手势开始中心、角度和手柄参考点；屏幕候选角减去地图总旋转后保存为图形自身角度。若中途越界，通过连续采样和二分截断到最近合法角度，不能跳过非法区间。

```text
shapeRotation = normalizeDegrees(screenRotation - totalRotation)
```

- 确认：保存 `rotatedRectCorners(...)` 得到的 Content 四角，而不是保存屏幕包围框。

因此，图形自身旋转和地图旋转是两个独立量：

```text
屏幕视觉角度 = shapeRotation + totalRotation
持久化几何角度 = shapeRotation
```

### 5.5 圆形禁区

圆形移动与矩形一致：从起始圆心和累计屏幕位移计算候选位置，先按圆的真实屏幕包围框在工作区外接矩形内限位，再将接受的屏幕位移转换为 Content 位移。

圆形缩放不再对旋转后的 `delta.x/delta.y` 求平均，而是把累计屏幕位移投影到“起始圆心 → 缩放手柄”的屏幕径向，再除以总缩放得到半径变化。候选半径同时受 `0.2 m` 最小物理尺寸和工作区外接矩形允许的最大半径限制。

若圆心移动正确但缩放不跟手，应检查是否错误地使用逐帧 delta、手柄当前位置或 x/y 平均值，而不是检查圆形自身旋转。

### 5.6 世界坐标下发边界

Step3 的屏幕交互最终都需要回到 Content/Bitmap 坐标，再由 ViewModel 转成世界坐标。确认数据时必须使用真实 Content 四角或圆心/半径，不能使用：

- `gestureBounds` 的四角；
- `toScreenRect(topLeft, bottomRight)` 生成的轴对齐框；
- 已经包含 `totalRotation` 的屏幕坐标。

否则会产生“编辑时正确，确认后偏移或角度改变”的典型问题。

### 5.7 工作区、多边形顶点和禁区边界

当前边界统一在屏幕空间处理：

- 工作区矩形移动、缩放和旋转使用旋转后地图的屏幕轴对齐外接矩形作为父边界，并按真实屏幕四角/包围框实时限位。
- 多边形顶点点击创建后，每个顶点都有稳定拖动命中区；目标屏幕点先钳制到地图外接矩形，再经 `toContentPoint(...)` 更新原索引位置，不自动重排，也不增加自交判断。
- 多边形关闭/确认按钮与首尾顶点错开，避免遮挡顶点拖动。
- 矩形和圆形禁区创建、移动、缩放、矩形旋转均限制在当前工作区的屏幕轴对齐外接矩形内，并按禁区真实屏幕几何做限位。

“外接矩形”不是严格多边形包含：旋转地图/工作区轮廓外侧的三角空白区域仍允许操作。这是当前明确的产品范围。如果未来要求严格包含，才需要新增点在多边形内和边相交判断，不能通过修改坐标逆变换实现。

## 6. 后续页面的旋转消费

### 6.1 Step4

`MapScreenStep4ViewModel` 将路径规划响应中的两个旋转字段写入 `MapGeo`。`MapScreenStep4` 把两者相加后传给 `FittedMapRobotMarker(mapRotationDeg = ...)`，组件内部使用：

```text
displayHeading = robotHeading - mapRotationDeg
```

### 6.2 地图首页和任务预览

`MapHomeViewModel` 的地图列表/预览模型已增加两个字段，并在接收 `MapPreviewPayload` 时透传。开始打磨页面对地图预览和规划预览分别计算：

```kotlin
val totalRotation = mapPreview.alignmentYawDeg +
    mapPreview.rotationAlignmentDeltaDeg
```

`StartGrindingMapPanel.TaskMapPanel` 根据当前步骤选择活动角度：规划预览图片存在时使用 `planPreview` 的两个角度字段，否则使用 `mapPreview`。底图、工作区轮廓和地图附着内容在同一个 `withTransform` 中绕面板中心旋转；障碍区编辑框保持屏幕轴对齐，便于用户操作。机器人位置仍通过地图坐标映射，朝向由 `FittedMapRobotMarker(mapRotationDeg = activeMapRotationDeg)` 抵消地图旋转。

工作区点击命中不能直接用旋转后的屏幕触点检查未旋转的工作区多边形。`findRegionIdAt(...)` 会先绕面板中心按 `-mapPreviewRotationDeg` 反向旋转触点，再执行多边形包含判断。

排查“Step3 正常、开始打磨页面不正常”时，应沿 `MapPreviewStream → MapHomeViewModel → StartGrindingMapPanel` 检查字段是否丢失，并核对当前步骤选择的是地图预览角度还是规划预览角度。

### 6.3 开始打磨规划避障区交互

规划避障区的 `TaskObstacleShape` 保存在面板基础 Model 坐标中，矩形和圆形始终保持屏幕轴对齐，不随地图角度偏转。`obstaclePlacementBounds(...)` 将图片适配矩形四角绕面板中心按地图角旋转后取 `min/max`，得到旋转地图的轴对齐外接矩形；创建、移动、缩放以及 Viewport 平移限位统一使用该范围。

交互遵循与 Step2/Step3 相同的稳定手势模型：

1. `ObstacleDragTarget` 和缩放按钮在手势开始时固定命中位置，记录起始 `TaskObstacleShape`、起始 Viewport scale 和累计屏幕位移。
2. 动态图形及删除、确认、缩放按钮继续跟随预览；可见按钮与固定命中层分离，避免右下角按钮在拖动时消失。
3. 屏幕位移只除以手势开始时的 Viewport scale，不叠加地图旋转逆变换，因为避障区 Model 轴与屏幕轴一致。
4. 矩形移动保证整个矩形位于地图外接矩形内；右下角缩放固定左上角，并受 `0.2 m` 最小物理尺寸和最大边界限制。
5. 圆形移动保证圆周不越界；缩放把累计屏幕位移投影到起始手柄径向，保持圆心固定，并限制最小/最大半径。
6. 候选 `TaskObstacleShape` 通过 `onObstacleChange` 回传给 `StartGrindingScreen`；页面以 `obstacleShapes` 列表和 `editingObstacleIndex` 管理多避障区，取消仅删除当前编辑项，确认保留该项并结束编辑。

越界时图形停在最近合法位置，反向回拖应立即恢复跟随。若出现拖动越来越慢、方向反复或按钮消失，应优先检查是否重新引入了逐帧 delta、动态命中位置或图形/按钮共用移动命中层。

### 6.4 开始打磨障碍区坐标下发

开始打磨页面的障碍区编辑框位于面板 Screen/Canvas 空间，不能把其角点直接当作 Bitmap 像素。当前实现通过 `onPanelSizeChanged` 保存 `TaskMapPanel` 的实际尺寸，并由 `canvasPointToMapWorld(...)` 完成完整逆变换：

```text
面板角点
  → 绕图片适配区域中心按 -totalRotation 撤销地图旋转
  → 撤销图片在面板中的居中和等比适配
  → 按归一化比例换算到原始 mapWidth/mapHeight 像素
  → 翻转 Y 轴并应用 resolution、originX、originY
  → 世界坐标
```

这里必须区分三个尺寸：面板尺寸、解码 Bitmap 尺寸和协议地图原始尺寸。图片使用 `ContentScale.Fit` 时通常会产生横向或纵向留白；如果直接使用障碍框面板坐标除以 Bitmap 宽高，会造成无旋转时也存在比例偏移。旋转必须在 Y 向下的 Canvas 空间先撤销，再进行 Y 轴翻转，避免角度符号再次变化。

`calculateObstacleWorldPoints(...)` 只有在四个角都成功转换时才返回一个障碍区，否则返回空列表，避免下发不完整多边形。`StartGrindingCoordinateTransformTest` 当前覆盖：

- `0°` 基础换算；
- `+90°` 和 `-90°` 正负号约定；
- 面板与图片宽高比不一致时的居中等比适配。

避障区交互改造不改变下发链：

```text
UI 矩形左上、右上、右下、左下
→ 绕图片适配区域中心按 -totalRotation 撤销地图旋转
→ 撤销 ContentScale.Fit
→ 映射到地图原始像素
→ 翻转 Y 轴并应用 resolution/origin
→ 按原点序生成 TaskObstacleRegionConfig
```

圆形仍按现有协议转换为其轴对齐包围矩形四角，不改变下发形状、ID 或点序。

### 6.5 障碍区协议标识与地图归属

Step3 地图编辑添加/删除障碍区时，`MapScreenStep3ViewModel` 会把当前 `mapId` 传给 `TcpManager`，避免地图编辑命令缺少地图归属。

任务配置中的 `obstacle_regions` 不能只设置 `points`。当前 `TcpManager.requestTaskConfig(...)` 按工作区时间编号思路生成障碍区标识：

```text
obstacle_region_<当天已过秒数 + 同批序号>
```

同一值写入 `region_id` 和 `name`，并补齐 `REGION_TYPE_OBSTACLE`、`enabled = true`、`closed = true`、`priority = 10`。序号偏移用于避免同一任务配置一次携带多个障碍区时出现重复 ID。若服务端按 ID 或名称持久化/去重，缺少这些字段可能表现为后一个无 ID 障碍区覆盖前一个。

### 6.6 APP 绘制任务规划路径

路径规划请求统一设置 `return_path_chunks = true`、`max_chunk_size = 2048`；设备状态页还会通过 `TaskPathRequest (0x0505)` 请求既有任务路径。`TaskPathChunk (0x0506)` 按 `task_id + path_version` 组包，完整 JSON 解析后发布到 `TaskPathStream`，残缺或损坏的分片不会覆盖上一版完整路径。

路径点是 `frame_id = map` 下的世界坐标（米），显示顺序为：

```text
世界坐标
→ 按地图 origin/heading 撤销世界姿态
→ 按 resolution 转原始地图像素并翻转 Y 轴
→ 映射到解码 Bitmap
→ ContentScale.Fit
→ totalRotation
→ 页面 zoom/pan
```

路径 JSON 的 `alignment_yaw` 只用于一致性检查；实际显示仍使用页面地图元数据中的 `alignmentYawDeg + rotationAlignmentDeltaDeg`，不能再次叠加。Step4、开始打磨预览和设备状态页共用同一变换，其中设备状态页把计划路径放在彩色实际轨迹下方。

## 7. 常见故障与排查路径

| 现象 | 优先检查 | 常见原因 |
| --- | --- | --- |
| Step2 滑动后地图不转 | `alignmentYaw`、`MapRotationController`、Canvas `rotate` | 状态未更新、控件被禁用、旋转中心错误 |
| Step2 返回页面后角度恢复 | 预览响应两个字段、Step2 初始化 | 下位机未保存，或响应未返回最新角度 |
| 下一步没有下发角度 | `MapAlignment_Debug` 日志链 | 下一步回调未调用、`mapId` 为空、TCP 发送失败 |
| 不同步骤地图角度不同 | 各处 `totalRotation` 公式 | 漏加 `rotationAlignmentDeltaDeg` 或重复叠加 |
| 地图正确但机器人朝向错误 | `robotHeading - totalRotation` | 未减地图角度，或位置与朝向使用了不同角度 |
| Step2 擦除区或 StartGrinding 避障区旋转后拖动方向偏转 | 几何空间、累计屏幕位移换算 | 对屏幕轴对齐图形错误叠加了 `-totalRotation`，或总缩放除法错误 |
| Step3 工作区/禁区旋转后拖动方向偏转 | `screenDeltaToContentDelta` | 保存真实 Content 几何时漏掉 `-totalRotation`，或总缩放不完整 |
| 图形拖动/缩放不跟手，越拖越慢 | 起始几何、累计位移、固定命中层 | 基于动态预览逐帧累加 delta，控件重组位置抵消了指针位移 |
| 右下角缩放按钮拖动时消失或中断 | 固定命中层、可见按钮位移 | 命中 Box 随预览移动，或按钮同时承担动态定位与手势捕获 |
| Step3 编辑框正确但确认后错位 | 确认数据源 | 保存了屏幕包围框，而非真实 Content 四角 |
| Step3 控件按钮不在图形角上 | `screenCorners`、`gestureBounds` | 把旋转矩形当作轴对齐 Rect；显示角与参考角混用 |
| 旋转手柄跳变 | `rotationReferenceHandleCenter` | 使用了包围框左下角直接计算真实矩形角度 |
| Step3 工作区初始水平但禁区初始倾斜 | `ForbiddenShape.rotationDeg` 创建值 | 禁区未调用 `initialBoundaryRotationDeg()` 抵消 Canvas 地图旋转 |
| 禁区越过工作区屏幕外接矩形 | `currentWorkspaceScreenBounds()`、候选真实屏幕几何 | 仍按 Content Rect 或逐帧位置限位，没有用真实四角/圆周包围框 |
| 禁区进入工作区真实轮廓外的三角区 | 当前产品边界约定 | 禁区按工作区屏幕轴对齐外接矩形限制，不做严格多边形包含 |
| Step3 新建矩形没有出现在小车附近 | `placeInitialBoundaryRect()`、`robotPoseToBitmapPoint()` | 小车定位无效触发地图中心回退，或仍使用固定 Content 初始坐标 |
| 擦除显示正确但下发坐标错误 | `alignedCorners` 回算链 | 未按 `-alignmentYaw` 还原，或 Bitmap/TCP 尺寸比例错误 |
| 开始打磨地图未旋转或预览切换后角度不对 | `activeMapRotationDeg`、预览类型 | 地图预览与规划预览角度选错，或只消费一个旋转字段 |
| 开始打磨工作区显示正确但点击不中 | `findRegionIdAt` 触点逆旋转 | 用旋转后屏幕触点直接检查未旋转工作区多边形 |
| 开始打磨障碍区视觉正确但下发坐标偏移 | `canvasPointToMapWorld`、面板尺寸、`previewImageRect` | 忽略 ContentScale.Fit 留白、未撤销地图旋转或混用 Bitmap/地图原始尺寸 |
| 多个任务障碍区下发后只剩一个 | `region_id`、`name` | 障碍区标识为空或重复，服务端按标识覆盖/去重 |
| 响应字段变化但 UI 不刷新 | Payload `equals/hashCode` | 新字段未加入比较，StateFlow 判断对象未变化 |

### 建议的最小联调矩阵

至少验证以下角度：

- `0°`：确认无旋转回归。
- `30°` 或 `45°`：发现坐标中心、缩放和包围框问题。
- `90°`：最容易发现是否错误增加或遗漏拖动增量的反向旋转。
- `-90°`：验证正负号约定。
- `180°` 和 `-180°`：验证边界限制和归一化。

每个角度至少覆盖：

1. Step2 地图和机器人显示。
2. 擦除框创建、连续长距离移动、边缘钳制、反向回拖、缩放、按钮持续可见、确认及下发坐标。
3. Step3 工作区矩形以小车中心初始化、边缘回退、移动、缩放、旋转、确认，以及从多边形切回矩形时重新定位。
4. Step3 多边形顶点拖动和点序；矩形禁区初始方向、矩形/圆形禁区移动、径向缩放、旋转及确认。
5. Step4 和开始任务页面的地图/机器人显示、工作区点击命中。
6. 开始任务避障区连续移动、边缘钳制、反向回拖、矩形锚点缩放、圆形径向缩放、按钮持续可见，以及适配留白区域附近的显示和下发坐标。
7. 退出后重新进入，确认后端返回角度与本地显示一致。

## 9. 当前实现注意事项

1. `core/sllink/src/message_gen/sl_link/SlLink.java` 是生成协议代码，本次本地差异非常大。排查协议字段时应优先确认其上游协议定义和生成过程，避免直接手改生成文件造成不可复现差异。
2. 当前 `MapAlignment_Debug` 包含较多联调日志和一次调用栈打印，适合排查下发链路；发布前可评估是否降级或删除，避免日志噪声。
3. Step2 使用 `alignmentYaw` 作为当前编辑角度，而 Step3/Step4 使用响应中的 `alignmentYawDeg + rotationAlignmentDeltaDeg`。因此 Step2 下发后，后续页面能否立即获得新角度依赖下位机保存和响应回传。
4. 旋转矩形的屏幕包围范围必须由四角转换后取 `min/max` 得到，不能只转换左上和右下两点。边界钳制必须检查候选真实屏幕几何。
5. 图形自身角度、地图角度和机器人 heading 的正负号约定不同。修改任一处前，应先明确该值属于 Content 角、屏幕角还是世界朝向，避免通过“多加/少减一个角度”局部修补。
6. Step2/Step3 工作区使用旋转地图的屏幕轴对齐外接矩形；Step3 禁区使用工作区屏幕轴对齐外接矩形；StartGrinding 避障区使用旋转图片适配矩形的外接矩形。这些边界均允许进入真实轮廓外的三角空白区，不等于严格多边形包含。
7. 开始打磨页面已使用 `List<TaskObstacleShape>` 保存多避障区，并由 `calculateObstacleRegions(...)` 逐项转换；新增、取消、确认和列表下发需要继续保持索引一致，避免删除当前编辑项后错改其他区域。
8. 障碍区任务 ID 使用“当天已过秒数 + 同批序号”。它解决同一配置内的重复问题；若服务端要求跨请求长期唯一，应与协议方确认是否需要加入任务 ID、地图 ID 或更稳定的全局标识。
9. 本地还存在与旋转非核心相关的地图擦除 ID、设备页面、Gradle 配置和页面日志等修改；出现回归时应通过 `git diff` 单独确认，不应默认归因于旋转变换。
10. 三组交互纯几何测试已经覆盖外接矩形、累计移动、反向回拖、锚点/径向缩放和 Step3 小车中心初始摆放；当前本机执行 Dev/Prod 单元测试仍可能被 Android SDK 平台元数据权限及缺失 Build Tools 35.0.0 阻塞，不能把环境失败误判为测试断言失败。

## 10. 快速排障原则

地图旋转问题通常不是单一绘制问题，而是把显示、手势和下发三个责任混在了一起。定位时遵循以下原则：

1. **先确认角度来源**：两个协议字段是否都到达当前页面，是否只相加一次。
2. **再确认几何所属空间**：当前变量是未旋转 Bitmap Content、已对齐 UI Content、面板 Model、Screen 点、屏幕累计位移还是世界坐标。
3. **按几何空间选择 delta 公式**：Step3 真实 Content 几何需要撤销地图旋转；Step2 和 StartGrinding 的屏幕轴对齐几何只除以缩放。
4. **检查手势生命周期**：是否保存起始几何、使用累计位移并固定命中层；不要用动态预览位置作为下一帧基准。
5. **检查屏幕边界**：用旋转后四角的轴对齐外接矩形和候选真实屏幕几何限位，越界后反向拖动必须能立即恢复。
6. **最后确认下发闭环**：UI 修复不能改变已经验证正确的反向旋转、Bitmap/TCP 比例、Y 轴翻转、世界坐标公式和点序；确认数据应保存协议所需的真实 Content 几何。

点从 Content 转到 Screen 后再转回应得到原点；同一手势在不同 zoom 下应具有一致屏幕跟随比例；相同角度和相同确认几何在交互改造前后必须得到完全相同的下发坐标。
