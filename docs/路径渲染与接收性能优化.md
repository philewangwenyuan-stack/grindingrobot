# 路径渲染与接收性能优化

2026-10-25，本地代码核实和优化。没有现场耗时日志，不能据此认定APP是多秒规划等待的主因；本次不修改板端调度器或规划算法。

## 已核实的问题

- `TaskPathGeometry` 原先在每次绘制时，按每个摘要段扫描整条路径，再逐点进行地图投影、适配和旋转，逐边调用画线。
- Step4图片已有`remember`缓存；不是每帧重新解码。图片变化时仍可能有一次同步解码开销，本次未更改图片解码机制。
- `SlLinkManager.handleReceivedData`逐帧同步处理。完整路径JSON原先在最后一片的接收回调中解析，会推迟同一接收批次后续ACK/状态帧的处理，即使接收线程是IO线程。
- 机器人标记原本已有独立图层；回放页则把静态规划路径和动态实际轨迹放在同一个Canvas中。

## 修改

`taskPathRenderSegments`为有效点index建立一次查找表，摘要只访问命中的点，再恢复原数组顺序。仍支持缺失/稀疏/重复/乱序index、重叠摘要和未覆盖点回退；无效坐标和未命中的数组间隙仍然断开。

`TaskPathProjectionCache`每个已挂载图层只保留一份当前路径。路径快照引用变化（即使版本相同）、原图元数据/版本、原图或解码尺寸、配色策略改变时重建。采用引用判断避免数据类大列表的深比较；仅显示对齐角、视口缩放/平移和机器人位姿变化时复用几何。不会建立无限增长的任务/版本全局缓存。

投影时三角函数和地图常数每次构建只算一次，先生成Bitmap坐标折线。`TaskPathDrawingCache`保留原生`Path`，逐段批量绘制，缩放、居中适配和旋转用Canvas矩阵完成。无效/越界点两侧不连线，孤立点保留，线宽维持原来的1.5px乘视口倍率。现有绿色路径、蓝色连接段和绘制顺序保持；原生折线圆角连接处与原逐边圆端点的抗锯齿可能存在少量像素差异。

Step4、开始任务预览、设备任务地图和回放共用`FittedTaskPathOverlay`。Step4/预览的路径和起终点分层，回放的地图、静态规划路径、动态实际轨迹分层。旧`drawFittedTaskPath`仅保留一次绘制兼容入口并标记废弃，生产页面均已迁移到保留缓存的图层。

`TaskPathDecodeQueue`使用应用作用域的Default单工作者，最多等待2份完整响应，正在解析和等待的原始JSON合计不超过64MiB。接收回调非挂起提交，接受的响应按完成组包顺序解析；超限返回保留request/task/map/version关联的空结果，明确结束该请求，不静默丢弃。字节限制只约束待解析原始数据，不代表解析后JSON对象和路径对象的总堆内存上限。

连接成功、断开或失败均清理未完成分片、等待队列并递增解析代次；已经开始的同步解析即使完成，也不能在重置后发布旧结果。组包/提交与重置共用锁。UTF-8仍在完整字节合并后解码，坏JSON仍发布空结果以结束本轮等待；协议和任务启动规则不变。

## 验证

- TCP模块94项测试通过，新增5项验证阻塞解析不阻塞提交、接受结果顺序、队列满、包含活动任务的字节预算、断线代次隔离、坏JSON/异常后继续处理、分片重置。
- 150组随机稀疏/乱序/重复index及重叠区间，与原全扫描算法逐段比较一致。
- 5万点、500摘要段的合成数据，首次分组208848次点读取；旧算法仅每段全表扫描即至少2500万次。同快照500次缓存查询没有额外点读取。初次JVM测试约31ms，仅为开发机合成测量，不能代表平板帧率或现场等待时长。
- 缓存与视口8项单测、原生UI8项通过；其中新增像素比较覆盖适配、正负旋转、180度、缩放、平移、孤立点与断段，另7项覆盖既有遥控/建图/全屏操作。完整APP及测试APK打包通过。日志及既有测试限制见`.planning/path-performance/progress.md`。
- 原`TaskPathGeometryTest`四项期望红色的断言仍是既有失败；当前产品绿色未改。本次没有重写这些断言，也未修复其他GNSS等无关测试。

仍需用现场相同大路径测量规划请求到响应、组包、后台解析和首帧显示的分段耗时，才能判断剩余等待来自规划、传输还是首次显示。没有操作或部署现场机器人。
